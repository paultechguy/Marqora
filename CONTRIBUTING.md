# Contributing to Marqora

Thanks for taking an interest. Bug reports, fixes and feature work are all welcome.

---

## Branches

`dev` is the default branch and where all work lands. `master` tracks what has been
released and only ever moves forward from `dev`.

**Open your pull request against `dev`.** One raised against `master` will be asked to
retarget, which is a wasted round trip for both of us.

Neither branch can be deleted or force-pushed, so a merged change stays merged.

How a release is actually cut — the scripts, the gates, and the order they run in — is in
[`docs/Releasing.md`](docs/Releasing.md).

## Before you write much

For a bug fix, or something small and self-evident, go straight to a pull request.

For anything larger — a new feature, a change to how something already works, a new
dependency — open an issue first and say what you have in mind. Marqora has opinions about
what it is, and it is far easier to agree on an approach before the code exists than to ask
for it to be rewritten afterwards.

## Building

The README covers this properly. The short version:

```powershell
pwsh .\build\Get-WebAssets.ps1     # once; third-party web assets are not in source control
dotnet build PaulTechGuy.MQ.slnx
dotnet test PaulTechGuy.MQ.slnx
```

You need the .NET 10 SDK and Windows. The build fails with a clear message if the web
assets are missing.

## What a change has to satisfy

**Every hand-written `.cs` file under `src/` and `tests/` starts with the licence header.**

```csharp
// Copyright (c) 2026 Paul Carver
// SPDX-License-Identifier: Apache-2.0
```

Two lines, then a blank line, before the usings or the namespace. This is not decoration:
`IDE0073` is set to warning in `.editorconfig` and `EnforceCodeStyleInBuild` is on, so a
file without one warns at build time. Do not add it to generated code — `obj/`, `bin/`,
`*.g.cs`, `*.Designer.cs`, or anything carrying an `<auto-generated>` marker.

Rather than editing files by hand, run the script. It is idempotent:

```powershell
pwsh .\build\Add-FileHeaders.ps1          # apply to anything missing or stale
pwsh .\build\Add-FileHeaders.ps1 -Check   # report only, non-zero exit if any are missing
```

**The build is clean.** No new warnings. `.editorconfig` is the authority on formatting and
is enforced at build time, so there is nothing to argue about and nothing to configure in
your editor.

**Tests cover what you changed**, where the change is testable. The layers below the UI were
written to make this easy — see the Tests section of the README. A project dropped under
`tests\` is picked up automatically.

**Marqora makes no network calls at runtime.** No telemetry, no update checks, no account,
no fetching anything. This is the point of the application rather than an implementation
detail, and a change that adds one will not be merged.

**The layering holds.** No concrete layer references another; they meet at the composition
root in `src/PaulTechGuy.MQ.App/Program.cs`. If a change seems to need a new project
reference, that is worth an issue before a pull request. `docs/Architecture.md` explains how
it fits together and why.

**Do not commit `webshell/vendor/`.** It is git-ignored and restored by
`build/Get-WebAssets.ps1`. Bumping a third-party version means changing that script and the
version table in the README.

## Pull requests

Keep one pull request to one concern. A focused change gets read and merged; a branch that
fixes a bug, renames some things and reformats a file is hard to review and tends to sit.

Write commit messages in the imperative — "Fix tab focus after closing the last tab", not
"Fixed..." or "Fixes...". Say why in the body if the why is not obvious from the diff.

Describe what you changed and how you convinced yourself it works. For anything touching the
UI, a screenshot saves a lot of back and forth.

Unrelated reformatting makes a diff unreadable. If a file genuinely needs tidying, that is
its own pull request.

## Reporting a bug

`Help > About Marqora` has a **Copy details** button that puts the version, runtime and
paths on the clipboard. Paste that in. `Help > Open Log Folder` goes to the logs, which
record errors from the preview's JavaScript as well as from the app.

Then the usual: what you did, what happened, what you expected instead. A markdown document
that reproduces it is worth more than a description of one.
